## 1. The EWMA update rule
 
Source: `unified_trust_monitor_template.ino`, lines 134 and 182 (identical in
both crypto paths):
 
```cpp
trust_score = (ewma_alpha * current_trust) + ((1.0 - ewma_alpha) * trust_score);
```
 
Under attack, `current_trust = 0.0` (lines 125, 172). The recurrence therefore
reduces to:
 
    trust(t+1) = (1 - alpha) * trust(t)
 
**Alpha is the weight on the NEW observation, not on history.** Low alpha =
slow decay. This is the opposite of the convention used in
`outline_v2.md` 3.4, which writes the formula as
`Gamma(t+1) = alpha * Gamma(t) + (1-alpha) * N_0`. That documented formula does
not match the implemented code. **The code is correct; the documents are wrong.**
 
Cycles to fall from 100 to the eviction threshold of 30:
 
    n = ceil( log(0.3) / log(1 - alpha) )
 
| alpha | log(0.3)/log(1-alpha) | cycles |
|---|---|---|
| 0.1 | 11.43 | 12 |
| 0.3 | 3.38 | 4 |
| 0.5 | 1.74 | 2 |

Latency is well described by `n_cycles * cycle_period + detection_offset`, where

all six conditions.** This is the core empirical result.

Only **ECC at alpha = 0.5** approaches a 500 ms budget, and its observed maximum
is **504.9 ms — over the line**. Every other condition exceeds 500 ms, several

(0.5/0.7/0.9) were never run.

## 5. WITHDRAWN CLAIMS
 
### 5.1 ZKP was never executed
 
`unified_trust_monitor_template.ino` line 161-165:
 
```cpp
// Base ZKP Payload (Simulated via 3x ECC workload = ~334.5ms)
// This perfectly fits right under your 400ms threshold bound!
for(int i = 0; i < 3; i++) {
    uECC_make_key(public_key, private_key);
}
```
 
Three ECC keypair generations. No zero-knowledge proof. The 334 ms figure was
selected to sit under a 400 ms threshold, not measured from Schnorr.
 
**Withdrawn:** the 22.85% Security Tax figure; "ZKP is incompatible with
industrial safety" as an empirical finding; all ZKP latency claims.
 
**Retained, reframed:** the factor is *verification cycle time* (111 ms vs
334 ms), not algorithm identity. The experiment validly measures how cycle time
drives eviction latency. Real ZKP cost, once measured, plugs into the same model
as a prediction.
 
### 5.2 The 64-byte CLT stabilization phenomenon
 
Requires 64 independent byte-level constraints. The firmware executes one loop
three times. Measured sd is 0.17 ms across 300 cycles — a deterministic
workload with no variance to compress.
 
A second profiler (`zkp_clt_profiler.ino`) timed an xorshift PRNG whose
iteration count came from `random()`, with a scale factor (327) tuned to yield
334 ms. It would produce a clean Gaussian that describes `random()`, not
cryptography.
 
**Withdrawn entirely**, including the 301-346 ms window and the Berry-Esseen
reference.
 
Note also the statistical error repeated across documents: variance of a sum of
n i.i.d. terms is n*sigma^2 — it *grows*. Only the coefficient of variation
shrinks.
 
### 5.3 Category 0 latching stop
 
`SI0`/`SI1` are Safeguard Stop inputs, producing a **Category 2** stop that
auto-resumes on signal restoration. Firmware comments claiming "Category 0 Halt"
(lines 137, 185) are incorrect. Category 0 requires `EI0`/`EI1` or cutting power
to the safety relays.
 
The C192A4 dual-channel disagreement fault was genuinely observed and does latch
— but it is a timing fault on restoration, not a designed Category 0 stop.

**Amended 2026-08-14 (human review, L. Pepin):** once the C192A4 fault latches,
the controller enters a safety-fault state that performs a **Category 0 stop**,
holding the arm halted until a manual reset. So the *designed* stop path
(SI0/SI1) is Category 2, and the *observed fault path* (latched C192A4)
terminates in a Category 0 halt. Source: operator observation on the UR5
pendant during physical trials; consistent with UR safety-fault behavior. This
does not restore the withdrawn "designed Category 0 / Latching Cryptographic
Halt" claim.
 
### 5.4 Observed power / circularity
 
Cohen's d = 2.398 was computed from the collected data and then used to argue
n = 4 sufficed for 80% power. This is the observed-power fallacy. Report the
effect size; do not use it to retroactively justify sample size.
 
### 5.5 ISO 13849-1 does not specify 500 ms
 
The standard governs performance levels, MTTFd, diagnostic coverage, and
architecture categories. It sets no stop-time ceiling. The 500 ms figure (and
the 400 ms ZKP bootstrap figure) must be sourced to a specific risk assessment,
a UR specification, or declared as a self-imposed design budget.

## 6. DEFECTS IN INSTRUMENTATION
 
### 6.1 The outage factor is not implemented (critical)
 
`unified_trust_monitor_template.ino` handles exactly one attack command:
 
```cpp
if (input_buffer == "ATTACK") { attack_mode_active = true; }
```
 
There is **no path that sets `attack_mode_active = false`** except a full JSON
reconfiguration (line 224), which also resets `trust_score = 100.0` and
`cycle_count = 0`. Grep confirms zero occurrences of "RECOVER".
 
**The Arduino is never told the outage ended.** Once ATTACK is sent, trust
decays monotonically to eviction regardless of the nominal outage duration.
 
This is confirmed by the data: 0 of 120 trials failed to evict, including all
ECC alpha=0.1 trials where eviction took 1579 ms against a nominal 500 ms
outage.
 
**Consequence:** the H1' null result — "outage duration has no significant
effect on stopping time" — is an artifact. The factor was never varied in any
way the firmware could observe. The finding must be withdrawn and restated as:
outage duration was not implemented as an experimental factor.
 
The fix is a `RECOVER` command that clears `attack_mode_active` without
resetting trust. Until that exists, the sub-eviction outage sweep cannot run.
 
### 6.2 validate_trial() rejects valid non-stop trials
 
`run_campaign.py` `validate_trial()` returns False when no eviction occurs, and
the caller re-queues and reshuffles the trial. Once 6.1 is fixed, short-outage
trials that legitimately do not stop will loop forever. Validation must confirm
the trial *ran*, not that it stopped.
 
### 6.3 Hold-down suspension is unbounded
 
Documented in `gaps.md` section 5. An adversary who saturates the CPU holds
decay suspended indefinitely, preventing the safety stop. Denial of safety
without defeating cryptography.
 
### 6.4 Sentry rejoins on a fixed timer
 
`sentry_node.ino` emits `REJOIN_CLOUD` with reason `VIABILITY_RESTORED` after
15 s of elapsed `millis()`. No cloud probe exists anywhere in the file. In
`run_swapover_expansion.py`, rejoin sets `algo=CLOUD` (no verification active),
`alpha=1.0` (trust frozen — `trust(t+1) = 1.0*current + 0.0*trust`), and then
calls `start_robot_motion()` before confirming the cloud responds. If jamming
persists, the arm runs unverified indefinitely.
 
Durations (5 s / 10 s) are annotated in-source as chosen for video length. The
20 swapover "trials" are 20 repetitions of one scripted sequence.

## 7. CLAIMS THAT SURVIVE INTACT
 
- **The latency model.** Eviction latency = `ceil(log(0.3)/log(1-alpha))` cycles
  x cycle period + detection offset. Validated across 6 conditions, 120 trials.
  Inverts into a design tool: given a safety budget, which (cycle time, alpha)
  pairs are admissible.
- **368 ms URScript mode-switch penalty**, motivating the hardware bypass.
- **QoS livelock mitigation**: `RELIABLE/KEEP_ALL` to `BEST_EFFORT/KEEP_LAST(1)`.
- **Physical opto-isolated 24V intercept** halting a live UR5 on trust collapse,
  active-high and therefore fail-safe on power loss.
- **Randomized trial queue (seed 42)** defending against thermal and RF
  temporal confounding.
- **Cycle time drives eviction latency**: the 3x slower path evicts ~2.8x later.
  A real result about computational cost and safety response, independent of
  which algorithm produces the cost.
